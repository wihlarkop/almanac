## 1. Product boundaries and data integrity

- Almanac is an **open-source, developer-facing model catalog + REST API**. The backend is the source of truth for model/provider metadata, alias resolution, validation, lifecycle, pricing, provenance and freshness. `almanac-web` is a separate *consumer/presentation UI*, not an alternate source of data truth.
- Keep the current Rust 2024 workspace (`server/`, `validator/`, `scraper/`), Axum/Tokio, declarative `providers/*.yaml`, `models/<provider>/*.yaml`, `aliases.yaml`, schemas and OpenAPI. Prefer small composable changes, no unrequested database, paid model proxy, user credential store or browser-specific backend.
- Snapshot on 2026-11-17: **817 model YAMLs, 62 provider YAMLs**. Scraper dispatch has **24 custom + 30 generic** provider entries; eight are missing (`haiper`, `hidream`, `kling`, `pika`, `reve`, `suno`, `synthesia`, `udio`). These are **coverage registration counts**, NOT live scraping success, API availability, pricing correctness or freshness guarantees.
- **Unknown is never zero/free/false/active/verified by default.** Audit and replace the existing writer's unverified `4096` context/output, `0.0` prices, guessed capability/status and current-date stamps. Use an explicit unverified/unknown representation and a deliberate schema compatibility path, never silently fabricate valid-looking catalog facts.
- Every changed model fact needs traceable provider/product source URL, precise field/value and verification date. Distinguish `official`, inferred, community and unknown confidence; official *source type* alone is not evidence that a record is still fresh. Preserve proper lifecycle (active/deprecating/deprecated/retired), aliases/replacement, supported API surface, regional restrictions and modality-specific pricing units.
- `pricing: null`, legitimately zero-cost tiers, unavailable public pricing and inapplicable per-token pricing are semantically distinct. Never compare token, image, audio-minute, video-second, character or credit prices as though interchangeable.

## 1A. Model **creator** eligibility — explicit owner decision 2026-11-17

- **`provider` denotes the company, research lab or organization that **authored/developed** the first-party model, not an inference hosting vendor, model marketplace, routing gateway, aggregator or cloud reseller.** The 62-provider baseline is not a cap: add new verified model creators as new official model families emerge. Record first-party lineage/ownership before adding a provider, model or alias. See [BE-16 #71](https://github.com/wihlarkop/almanac/issues/71), [BE-20 #75](https://github.com/wihlarkop/almanac/issues/75).
- Companies that both **create and host** models are eligible **only for the models they developed**. Example distinctions: own model families from Amazon (Nova/Titan), Microsoft (Phi), Google (Gemini/Gemma) and IBM (Granite) are eligible; third-party models available through their cloud catalogs do **not** become these companies' models. A host that develops a distinct original model can be included only for that model, based on primary-source evidence.
- First-party models qualify whether API-only, open-weight, proprietary, generative, embedding, reranking, **typed decision/System One**, audio, image, video or 3D. Do **not** equate model provider with where the inference runs, nor relabel ordinary hosted fine-tunes/quantizations/wrappers as original models without verifiable independent model authorship.
- Provenance review must capture maker/organization, model family and version, official URL, first-party ownership evidence, supported modality, licensed/API availability, and separate distribution routes when useful. Classify `VERIFIED_CREATOR`, `CANDIDATE`, `HOST_ONLY_EXCLUDED`, or `AMBIGUOUS_REVIEW` with rationale; never automatically delete old entries without a reviewed compatibility/migration plan.
- **Example current candidate:** TypeSafe AI is the creator/provider; **Jev** is the model family. Its System One typed probabilistic judgments are not a chat-completion model. See [BE-17 #72](https://github.com/wihlarkop/almanac/issues/72) for official references and a proposed safe onboarding, not automatic authorization to scrape or publish.

## 2A. Scraper v2 source-first, typed-evidence architecture

- Treat the scraper as **discovery plus evidence collection**, not an authoritative truth engine: verified provider identity → public official API/OpenAPI or changelog/RSS/sitemap → HTML/static/structured docs → optionally authorized JS-rendered browser extraction → **typed candidate + per-field provenance** → deterministic diff → human review → validator → Git PR.
- A common bounded **transport layer** ([BE-03 #57](https://github.com/wihlarkop/almanac/issues/57)) owns HTTP status, retry/backoff, host/redirect allowlists/SSRF prevention, rate/byte/page/time budgets, cancellation, ETag/Last-Modified and distinct success/partial/no-data/blocked/error receipts. It must not silently treat 403, 429, failed JS or an empty source as model deprecation.
- **Provider adapters** ([BE-18 #73](https://github.com/wihlarkop/almanac/issues/73)) own per-source extraction of actual model IDs/spec/prices from **official public sources** with lower-risk structured sources preferred over generic `<code>` pattern matches. Browser/Kumo transport is optional and must comply with the source's permitted access; no stealth, anti-bot circumvention, private pages, unauthorized tokens or paid calls.
- **Evidence and review** ([BE-19 #74](https://github.com/wihlarkop/almanac/issues/74)) track verified field, original URL, retrieval/verification time, parser version and conflicts; distinguish discovered vs verified model, creator, lifecycle, pricing and modality. Changes must be reviewed, never auto-applied to trusted YAML. Store a rollbackable last-known-good snapshot.
- **New lab/company discovery** ([BE-20 #75](https://github.com/wihlarkop/almanac/issues/75)) produces **candidates only**, screens for model authorship and drafts additions for human review. Scheduled execution via [BE-12 #66](https://github.com/wihlarkop/almanac/issues/66) remains separately authorized, and no issue/roadmap implies a running monitoring task.

## 3. Maximum-safe multi-feature, multi-agent batches

- Owner may authorize **multiple independent features (A, X, C, Y)** in one batch, each subdivided into independent components (A1–A5). Parent coordinator maps issue -> owner/model -> branch/worktree -> exact base -> prerequisites -> reserved paths -> observable result. Each writable task gets its own isolated worktree. No arbitrary concurrency cap; respect real harness limits, available RAM/CPU and actual independence.
- Each feature has an accountable integrator and one reviewable **Draft PR by default**. Optional per-component PRs, traceable stacks and one batch integration PR are allowed if dependency chain and inclusion are explicit. Component helpers can feed a feature branch; **PR count need not equal child task count**.
- A feature integrator may combine independent component work on a dedicated **non-main** integration branch; a batch integrator can fan-in feature branches in another clean worktree. Single writer resolves shared-file conflicts. Never overwrite other writers' branches, force-push without approval or discard dirty user changes.
- **Dependency DAG, not global wave barriers:** independent READY work can proceed simultaneously. Downstream code starts only after all strict prerequisites are genuinely incorporated into an inspectable, owned integration base with an explicit stack/lineage **within an owner-authorized batch**; for `main`-ready PRs require independent ChatGPT review of the final combined tree before merge. A schema/security/data-integrity gate cannot be bypassed by stacking. Cross-repo consumers wait for a compatible backend contract/deployment when required.
- Do not ask for per-subagent or per-feature owner QA. Complete the authorized independent batch, hand off **one consolidated review manifest** and **one final manual acceptance round** for API/catalog behavior. CI/checks still run during implementation; owner manual acceptance is distinct.
- **Section 0B is a hard, fail-closed model gate**, not a preference: Luna XHigh parent, Luna Low–High children, Astra explicitly forbidden. No dispatch/spending quota when the harness cannot enforce and verify the selected model. Do not invent runtime identity or nested-agent availability.

Do not wait for unrelated provider cohorts; preserve strict source/contract dependencies, separate writer worktrees, one shared scraper writer and existing CI/actual rate limits. - **Source-first and evidence-first:** prefer meaningful safe scraper/API data code over repeated generic blocker docs only where specific contract/source evidence is ready. - **Issue closeout:** once the **entire issue's authorized deliverable** has independently reviewed exact-HEAD GO and verified safe merge (or approved research/design completion), ChatGPT should close that **truly completed issue** promptly with a factual PR HEAD, merge SHA, scope and `completed` disposition. Codex never merges `main` or closes issues. Keep partially implemented provider cohorts, in-progress scraper source, unresolved source verification, QA- or release-gated issues OPEN; an independently finished design-only issue or scoped batch tracker may close without implying full provider rollout.
